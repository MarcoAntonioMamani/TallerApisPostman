Autenticación: cómo demostrarle a la API quién eres

La mayoría de las APIs no responden a cualquiera: piden credenciales. En Postman se configuran en la pestaña Authorization, y Postman arma el header correspondiente al enviar. Aquí verás los tipos más usados, qué viaja realmente en cada uno y cómo configurarlos con APIs públicas de práctica.
🪪 Autenticación: ¿quién eres?La API verifica tu identidad. Si faltan o fallan las credenciales responde 401 Unauthorized.
🚦 Autorización: ¿qué puedes hacer?Ya sabe quién eres, pero revisa si tienes permiso para esa acción o ese dato. Si no lo tienes, 403 Forbidden.

🔍 Hallazgos para investigar en estas APIs

Token inválido → 500GET /auth/me en DummyJSON con un token inventado responde 500 "invalid token". Debería ser 401: un token malo es un error del cliente, no del servidor.
Clave incorrecta → 400El login de DummyJSON con contraseña equivocada responde 400 "Invalid credentials". Lo habitual es 401. ¿Qué dice su documentación?
Sin token → 401 ✓Sin header Authorization, /auth/me responde 401 "Access Token is required". Este sí es el comportamiento correcto.

Buenas prácticas

🔐 Credenciales en variables secretUsuario, clave, API key y token van en variables tipo secret, con el Initial value vacío. Nunca escritos en el request.
🧬 Auth en la colecciónConfigura la autenticación una vez en la colección y deja los requests en Inherit auth from parent. Si cambia, se cambia en un solo lugar.
⏱ Tokens que vencenLos tokens expiran. Obtén uno nuevo con un request de login y guárdalo con un script; no copies y pegues tokens a mano.
Idea clave: todos los tipos terminan en lo mismo: un dato extra en el request (casi siempre el header Authorization) que la API verifica. Al probar, revisa siempre los tres casos: con credenciales correctas (200), sin credenciales (401) y con credenciales inválidas (401/403).
