El estándar más usado es OpenAPI (antes llamado Swagger), y la página que lo muestra de forma visual es Swagger UI. Abajo hay una réplica interactiva del Swagger Petstore, una API pública de práctica que usaremos en todo el taller. Recorre sus partes o explórala libremente: haz clic en los endpoints.

    Del archivo OpenAPI a Postman en un paso

    📄 El archivo detrás de la página
    Swagger UI solo dibuja un archivo JSON o YAML que describe toda la API. Ese archivo es el contrato. Este es un fragmento del de Petstore:
    "host": "petstore.swagger.io",
"basePath": "/v2",
"paths": {
  "/pet/{petId}": {
    "get": {
      "summary": "Find pet by ID",
      "parameters": [{ "name": "petId", "in": "path",
                       "required": true, "type": "integer" }],
      "responses": {
        "200": { "description": "successful operation" },
        "404": { "description": "Pet not found" }
      }
    }
  }
}
    ⚡ Importarlo a Postman
    Postman puede leer ese archivo y crear una colección con todos los endpoints, ya armados:
    1. En Postman, botón Import (arriba a la izquierda).
    2. Pega la URL https://petstore.swagger.io/v2/swagger.json
    3. Elige Postman Collection y presiona Import.
    4. Aparece la colección Swagger Petstore con carpetas pet, store y user.
    💡 En el taller armaremos los requests a mano para entender cada parte. En el trabajo diario, importar la documentación ahorra mucho tiempo.

    ⚠ Son APIs públicas y compartidas: lo que crees ahí lo puede ver cualquiera, y lo que crean otros puede cambiar tus resultados. Usa siempre datos ficticios e ids propios (por ejemplo, tu número de lista + fecha), nunca información real.
    Idea clave: la documentación es el contrato de la API: dice qué endpoints existen, qué datos reciben, qué responden y cómo autenticarse. Al probar, la pregunta siempre es: ¿la API hace lo que dice su documentación? Si responde algo que no está documentado, o no responde lo que promete, es un hallazgo.
