Tipos de pruebas de una API

Una misma API se prueba desde distintos ángulos. Cada tipo de prueba responde una pregunta diferente y encuentra defectos distintos. Elige un tipo y ejecuta los ejemplos animados (datos y API ficticios).

Prueba funcional: se envía un request con datos conocidos y se compara la respuesta real contra la esperada. No basta con que “responda”: tiene que responder correctamente, también cuando los datos son inválidos.

PostmanNewmanKarateREST Assured
Qué se valida
  • Status code correcto (200, 201, 404…)
  • Body: campos, tipos y valores
  • Reglas de negocio y casos negativos
  • Efecto en los datos (consultar después)

Prueba de carga: se simulan muchos usuarios virtuales (VUs) llamando a la API al mismo tiempo, y se miden los tiempos y errores. Se define antes qué es aceptable (umbrales), por ejemplo: el 95 % de las respuestas en menos de 800 ms y menos de 1 % de errores.

Prueba de seguridad: se intenta usar la API como no se debería: sin credenciales, con permisos de otro usuario, con datos maliciosos o abusando de ella. Lo esperado es que la API lo impida con una respuesta controlada (401, 403, 400, 429…).

Qué se valida
  • Autenticación: sin token o con token vencido
  • Autorización: acceder a datos de otro usuario
  • Validación de entradas maliciosas
  • Exposición de datos y límite de intentos
⚠ Las pruebas de seguridad se ejecutan solo en ambientes de prueba y con autorización. Probar la seguridad de un sistema sin permiso no es una prueba: es un ataque.

Otros tipos de prueba que vas a escuchar

🔥 SmokeUnas pocas pruebas rápidas para confirmar que la API “está viva” después de un despliegue.
🔁 RegresiónVolver a ejecutar las pruebas existentes para confirmar que un cambio no rompió lo que ya funcionaba.
📜 ContratoVerificar que la API cumple su documentación (OpenAPI / WSDL): campos, tipos y formatos.
🔗 IntegraciónProbar la API junto con los sistemas de los que depende: BD, servicios externos, colas.
🧭 End-to-endUn flujo completo de negocio: login → crear → consultar → pagar, de punta a punta.
Idea clave: los tres tipos se complementan. Una API puede pasar todas las pruebas funcionales y aun así caerse con 100 usuarios (carga) o dejar que un cliente vea los datos de otro (seguridad). En este taller, la Parte 2 trabaja las funcionales con Postman y la Parte 3 las de carga.
