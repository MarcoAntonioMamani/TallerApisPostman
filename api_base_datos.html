De la API a la base de datos

Cuando llega un request, la API no guarda ni busca datos “por arte de magia”: pide una conexión a la base de datos, ejecuta una consulta (un SELECT, un INSERT, un procedimiento almacenado…) y devuelve la conexión. Elige un escenario y observa qué se ejecuta en la base de datos. Todos los datos son ficticios.

Conceptos que aparecen en la animación

🧩 Capas de la APIEl controller recibe el request, el servicio aplica las reglas de negocio y el repositorio es el único que habla con la base de datos.
🔌 Pool de conexionesAbrir una conexión a la BD es costoso, así que la API mantiene unas pocas abiertas y las presta a cada request. Si una no se devuelve, el pool se agota.
📦 Procedimiento almacenado (SP)Un conjunto de instrucciones SQL guardado dentro de la base de datos, con nombre y parámetros: EXEC sp_registrar_pago @monto=450. Muy común en sistemas bancarios.
🧷 ParámetrosLos valores del request viajan como parámetros (@id), separados del texto del SQL. Así la BD nunca confunde un dato con una instrucción.
🔒 TransacciónAgrupa varias instrucciones en una sola unidad: o se aplican todas (COMMIT) o ninguna (ROLLBACK).
🗑️ Borrado lógicoEn lugar de borrar la fila, se marca como eliminada. Se conserva el historial para auditoría, algo habitual en entidades financieras.
Idea clave: un 200 OK no garantiza que los datos quedaron bien. Una API puede responder “éxito” y aun así haber guardado un pago dos veces, dejado una transferencia a medias o agotado sus conexiones. Por eso, al probar, también se verifica el efecto en los datos: consultar de nuevo el recurso, contar registros, revisar saldos, y probar con varios usuarios y datos reales en volumen.
