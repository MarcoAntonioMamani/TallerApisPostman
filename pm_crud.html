CRUD completo con datos en tiempo de ejecución

Vamos a crear, consultar, actualizar y eliminar una mascota en Petstore. La clave profesional: nada se escribe a mano entre un request y otro. El primer request genera los datos, un script guarda el id en una variable, y los siguientes requests la usan. Así la colección se puede ejecutar mil veces, siempre con datos nuevos.

El flujo: cómo viajan los datos entre requests

Presiona Ejecutar y observa cómo se llenan las variables y cómo las usan los requests siguientes.

▣ Environment: Petstore - QA

Ejecuta el flujo dos veces: cada ejecución crea una mascota distinta con los mismos requests.

Laboratorio: arma la colección paso a paso

Cómo debe quedar cada request

POST 01 Crear mascota

URL
{{baseUrl}}/pet
Scripts → Pre-request
// Datos nuevos en cada ejecución
pm.environment.set("petId", Date.now());
pm.environment.set("petName", pm.variables.replaceIn("{{$randomFirstName}}"));
Body → raw → JSON
{
  "id": {{petId}},
  "category": { "id": 1, "name": "Perros" },
  "name": "{{petName}}",
  "photoUrls": [],
  "tags": [],
  "status": "available"
}
Scripts → Post-response
pm.test("Status 200", () => pm.response.to.have.status(200));
const json = pm.response.json();
pm.test("Se creó con el nombre enviado", () =>
  pm.expect(json.name).to.eql(pm.environment.get("petName")));
// Guardar el id que confirmó la API
pm.environment.set("petId", json.id);

GET 02 Consultar mascota

URL
{{baseUrl}}/pet/{{petId}}
Scripts → Post-response
pm.test("Status 200", () => pm.response.to.have.status(200));
const json = pm.response.json();
pm.test("Es la mascota creada", () => {
  pm.expect(String(json.id)).to.eql(String(pm.environment.get("petId")));
  pm.expect(json.name).to.eql(pm.environment.get("petName"));
});
console.log("Estado actual:", json.status);
No valida el status a propósito: así sirve para consultar antes y después de actualizar. Es el mismo request, reutilizado.

PUT 03 Actualizar mascota

URL
{{baseUrl}}/pet
Body → raw → JSON
{
  "id": {{petId}},
  "category": { "id": 1, "name": "Perros" },
  "name": "{{petName}}",
  "photoUrls": [],
  "tags": [],
  "status": "sold"
}
Scripts → Post-response
pm.test("Status 200", () => pm.response.to.have.status(200));
pm.test("Quedó vendida", () =>
  pm.expect(pm.response.json().status).to.eql("sold"));

DELETE 04 Eliminar mascota

URL
{{baseUrl}}/pet/{{petId}}
Headers
api_key : {{apiKey}}
Scripts → Post-response
pm.test("Status 200", () => pm.response.to.have.status(200));

GET 05 Verificar eliminación

URL
{{baseUrl}}/pet/{{petId}}
Scripts → Post-response
pm.test("Ya no existe: 404", () => pm.response.to.have.status(404));
💡 ¿Y PATCH? Petstore no tiene un endpoint PATCH: para cambiar datos usa PUT con el objeto completo. Ese es justamente un dato que se aprende leyendo la documentación.
Idea clave: cada request deja preparado lo que necesita el siguiente. El POST genera y guarda petId; GET, PUT y DELETE lo leen con {{petId}}. Por eso la colección se ejecuta completa, en orden, sin tocar nada: la base para el Collection Runner y la automatización.
