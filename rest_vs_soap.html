REST vs SOAP

Son dos formas de construir servicios web. Las dos viajan sobre HTTP, pero cambia cómo se escribe el mensaje, cómo se define el contrato y cómo se reportan los errores. Abajo se envía la misma operación a ambos servicios al mismo tiempo.

Diferencias principales



  
RESTSOAP

  
¿Qué es?Un estilo de arquitectura: reglas para usar HTTP de forma ordenada.Un protocolo estándar (W3C) con reglas estrictas para el mensaje.

  
FormatoNormalmente JSON (también XML, texto, etc.).Siempre XML dentro de un Envelope.

  
Cómo se identifica la operaciónPor la URL + método: GET /clientes/123.Por el nombre de la operación dentro del XML. Casi siempre usa POST a una única URL.

  
ContratoOpenAPI / Swagger (opcional, pero recomendado).WSDL obligatorio: define operaciones, tipos y la URL del servicio.

  
ErroresStatus codes HTTP: 400, 404, 409, 500…Un bloque <soap:Fault> en el XML, normalmente con HTTP 500.

  
Tamaño del mensajeLiviano.Más pesado: el envelope y los namespaces agregan texto.

  
SeguridadHTTPS + tokens (OAuth 2.0, JWT, API keys).HTTPS + WS-Security (firma y cifrado dentro del mensaje).

  
EstadoSin estado (stateless): cada request trae todo lo necesario.Normalmente sin estado, aunque los estándares WS-* permiten flujos con estado.

  
CacheLas respuestas GET se pueden cachear.Al ser POST, no se cachea por HTTP.

  
Herramientas para probarPostman, Newman, k6, curl, Karate.SoapUI, Postman (con XML), Karate, k6.





Ventajas y desventajas



  

    
REST

    
    
      
  • Simple de leer, escribir y depurar.
    • 
      
  • Mensajes livianos: ideal para apps móviles y web.
    • 
      
  • Aprovecha HTTP: métodos, status codes, cache.
    • 
      
  • Fácil de consumir desde cualquier lenguaje o navegador.
    • 
      
  • ✕ Sin un contrato estricto por defecto: depende de documentarlo bien (OpenAPI).
    • 
      
  • ✕ Cada equipo puede diseñarlo distinto si no hay estándares internos.
    • 
    

  

  

    
SOAP

    
    
      
  • Contrato estricto (WSDL): cliente y servidor saben exactamente qué esperar.
    • 
      
  • Validación de tipos con XSD antes de procesar.
    • 
      
  • Seguridad a nivel de mensaje (WS-Security), útil entre instituciones.
    • 
      
  • Muy presente en sistemas bancarios, core y legados.
    • 
      
  • ✕ Mensajes grandes y difíciles de leer a simple vista.
    • 
      
  • ✕ Más lento de desarrollar y más pesado de procesar.
    • 
    

  





¿Dónde se encuentra cada uno?



  
RESTApps móviles y webConsultar saldos, listar productos, registrar solicitudes.

  
RESTMicroserviciosServicios pequeños que se comunican entre sí dentro de una plataforma.

  
SOAPCore bancario y sistemas legadosServicios construidos hace años que siguen siendo críticos.

  
SOAPIntegraciones entre institucionesEntes reguladores, aseguradoras, pasarelas que exigen contrato formal.






  Idea clave: no es que uno sea “mejor”. REST domina en servicios nuevos por su simplicidad; SOAP sigue vivo donde se necesita un contrato estricto o donde ya existe una integración estable.
  Es común que una misma empresa tenga ambos: una API REST moderna que, por detrás, llama a un servicio SOAP del sistema central. Al probar, hay que saber leer los dos formatos.
